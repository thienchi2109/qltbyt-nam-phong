# TM-06 — Deviation and corrective action implementation plan

## Goal

Turn every out-of-range reading into a trackable deviation with mandatory corrective action.

## Scope

- One deviation per out-of-range reading, with Nhẹ/Nghiêm trọng/Khẩn cấp severity.
- Immediate action, owner, due date, cause, evidence and verification result.
- Canonical lifecycle: `Mở` → `Đang xử lý` → `Chờ xác minh` → `Đã đóng`; cancellation from `Mở`/`Đang xử lý` only with an authorized reason.
- Optional two-way link to an existing repair request; no automatic repair request creation.

## Acceptance criteria

- An out-of-range save creates or safely returns its deviation without duplicate creation under retry.
- The deviation shows the measurement and threshold snapshot that triggered it.
- Closing is blocked until immediate action and verification result are present.
- Repair links preserve independent lifecycles and permissions.

## Data, trust and transaction contract

- Case identity: UUID, unique `reading_id`, unique triggering reading-event id, equipment FK, immutable complete triggering event snapshot, optional triggering amendment id, severity/status, immediate action, owner, due date, cause, evidence, verification result, optional repair id, revision and UTC creation/update/decision metadata. Trigger copies event payload exactly, not latest reading/review/configuration. No direct client table access; RLS enabled, revoke PUBLIC/anon/authenticated table privileges, public RPC execute authenticated only, internal helper/trigger functions not callable by clients; all SECURITY DEFINER functions have explicit `search_path=public,pg_temp`.
- Case constraints: exactly approved severity/lifecycle strings; nonblank bounded supplied text; required immediate action and verification result for `Đã đóng`; mandatory nonblank reason on severity change/reassign/cancel at RPC boundary; valid finite due timestamp/date; valid active same-tenant/department owner; same-equipment repair. Plain bounded evidence text/reference uses existing note conventions, no upload/new storage or server-side URL fetch. Fields may remain unset while collecting actions; do not require cause/evidence/owner/deadline merely to record the triggering breach.
- Identity comes only from signed JWT and DB relations; never trust client owner/tenant/equipment claims as authorization. Resolve reading→equipment; use `_temperature_monitoring_assert_scope`. Expected revision is nonnegative mandatory; return a typed recoverable `outcome=conflict` with currently authorized case for stale writes, matching TM-05 response style. Unknown IDs/out-of-scope both fail `42501` without record leakage.
- New breach-event trigger materializes case plus opening audit atomically; existing-reading retry remains existing slot-conflict response and callers can look up case by reading. Migration backfills prior `deviation_created` events with `ON CONFLICT(reading_id) DO NOTHING`; no synthetic deviations for in-range/unable-to-measure rows. Backfill actor/time/snapshot come from original event, not migration actor/time. Trigger and backfill share the insertion routine so future and historical behavior agree.
- Lock order for writes: existing tenant advisory lock → equipment share lock/recheck → reading lock where amendment/measurement already requires it → case row `FOR UPDATE`; operations involving repair additionally follow equipment → repair lock before case lock and recheck repair equipment/permissions under lock. Case mutation must not lock a reading after locking its case. This avoids reversal against breach creation and existing repair writers; concurrent equipment movement is serialized by equipment lock/recheck.
- Use a single explicit action RPC with approved operation names (`update_action`, `assign`, `severity`, `start`, `submit_verification`, `close`, `cancel`, `link_repair`) and typed optional fields, rejecting unsupported fields per action. Avoid a generic JSON patch that could set internal status/actor/snapshot/revision fields. Writer action inputs and progress transitions are distinct from manager-only fields/operations.
- Mutation/event insert share one transaction; if audit cannot be inserted raise and roll back projection. Case events preserve before/after/action/reason/actor/time; immutable trigger blocks update/delete. Before looking up or returning any existing action request UUID, revalidate current equipment scope and action capability (including raw `admin` support). Return a fresh authorized case projection for matching actor/action/payload; never return an old snapshot after scope/capability changed. Reuse with different input is invalid. Unique request key scoped to case and revision locking prevent duplicate events under retries, double click and cross-session races. Stale different operations conflict, not silent merge.
- Lifecycle is fixed forward-only progression, plus approved cancellation from `Mở`/`Đang xử lý`; no implicit reopen or automatic close/cancel on corrected measurement/closed repair. `close` records verification result and requires existing/new nonblank immediate action, managers may self-verify. Approved amendments recompute slot status using TM-05 independently; first breach snapshot/case remain even if effective value becomes in-range. Later breaches on same canonical reading do not create another case.
- Repair link set/unset/change checks both temperature-manager authorization and `repair_request_get`; exact equipment equality is mandatory. Case→repair and repair→cases reads each recheck their own scopes. A private `BEFORE UPDATE OF thiet_bi_id` trigger on `yeu_cau_sua_chua` rejects changed equipment while any case links that repair (`23514`); it never alters status, case links or equipment. Link action locks repair row before rechecking equipment and persisting link, so a concurrent direct retarget serializes and either link validation fails or retarget guard rejects. Guard checks case existence without acquiring case locks. Existing public repair update does not retarget; unlinked direct retarget remains outside this guard. No automatic unlink/retarget. Read counts come from same scoped/filter predicate as items.
- Query API: detail by reading/case, list with 30-day default/explicit 7/30/90/custom up to 90 days over monitoring date, optional equipment/status/owner/severity/repair filters, max page size and stable `(monitoring_date,id)` cursor; history bounded cursor per case. Validate inverted ranges, oversized limits and malformed cursors. Do not cap historical retention/export policy or broaden TM-09 scope.
