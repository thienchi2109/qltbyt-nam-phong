# TM-05 — Confirmation, amendment and audit history

- Status: In Progress
- Milestone: Temperature Monitoring / Core workflow
- Depends on: TM-04
- Master spec: `docs/specs/temperature-monitoring.md`

## Goal

Make confirmed readings traceable and immutable while supporting controlled correction.

## Scope

- `Chờ xác nhận` review for abnormal readings and amendments.
- Approve/reject amendment flow with mandatory reason and distinct operator/approver.
- Reopen by authorized manager with mandatory reason.
- Domain history plus audit events that retain original and effective values.

## Acceptance criteria

- Confirmed readings cannot be updated or physically deleted through normal RPCs.
- An amendment preserves the original, records reason/actors/timestamps and becomes effective only after approval.
- Reopen creates an auditable event and returns the slot to the correct review state.
- History is tenant-safe and separate from broad equipment lifecycle history.

## Approved contract (2026-10-18)

Established requirements: original value/reason/operator/observation time/note and captured policy never change; proposals only become effective on approval; proposal/approval/rejection/reopen reasons are mandatory; authors, original operator and decision actors remain attributable; rejected proposals survive; every state change is append-only and atomic. Historical amendments use the original lower/upper/policy/shift snapshot, never today's policy. TM-06 deviation lifecycle remains deferred.

Owner approved the three recommendations on 2026-10-18; lead approved the technical checkpoint. Implementation below follows these decisions.

1. **Capabilities:** amendment authors use the already-approved recording roles/scopes. Confirmation and amendment decisions: `global/admin/to_qltb` only; reopen: the same manager roles. Retain current tenant AND department restriction for every non-global mutation. `regional_leader`, `user`, unknown/missing roles cannot write. Approver must differ from both original reading operator and amendment author, including global/admin. Owner approved this matrix on 2026-10-18.
2. **Review projection (approved):** untouched in-range reading is effective `Đã ghi`; unreviewed abnormal reading enters `Chờ xác nhận` with `effective_status=Bất thường` and `review_required=true`; confirmation yields `Bất thường` without replacing its value. Explicit reopen yields `Chờ xác nhận`; confirming it restores the effective classification. Confirmed unable-to-measure uses `slot_status=Đã ghi`, `is_unable_to_measure=true`, `value_c=NULL`, reason preserved and `review_required=false`/`review_state=confirmed`; it must never count or be interpreted as a measured or in-range numeric result.
3. **Amendment policy (approved):** allow one pending proposal per reading, including while its original review is outstanding. A proposal may replace a numeric value with another numeric value or an unable reason, or replace an unable reason with a numeric value; preserve original capture metadata. Reason and proposed value/reason are immutable. Reject restores the EXACT prior effective/review state, including outstanding abnormal/unable/reopen review and its unable flag; it must not accidentally confirm the original. Approval confirms the new effective value/reason using original thresholds. Managers may reopen any settled confirmed result, including unable-to-measure, with no pending proposal; repeated reopen is rejected. Owner approved these choices on 2026-10-18.
4. **Stale writes:** expose a monotonically ordered revision from the append-only stream; each mutation requires `expected_revision`. Lock canonical reading, then compare current revision and pending proposal. Approve/reject also require the exact `amendment_id` currently pending at that revision; confirm/reopen reject an amendment target and cannot bypass a pending proposal. A stale authorized request returns typed `outcome=conflict` with current revision/state and creates no event. Authentication/current equipment authorization precede conflict projection, so a stale/cross-scope request discloses no unauthorized state. Never use timestamp-only ordering or silently merge races.
5. **Minimal RPC surface:** `temperature_monitoring_reading_get(reading_id)` returns original/effective value-or-reason, captured snapshot, review flags, pending proposal and revision; `temperature_monitoring_amendment_create(reading_id,expected_revision,value_c,unable_reason,reason)`; `temperature_monitoring_reading_review(reading_id,expected_revision,action,reason,amendment_id)` with a bounded action enum `confirm|approve_amendment|reject_amendment|reopen`; `temperature_monitoring_reading_history(equipment_id,from,to,cursor,limit)` returns paginated dedicated domain/audit events. All validate claims/scope first. No client actor, threshold or effective-state input. Non-null expected revision/reasons required; proposal reason, decision reason and proposed unable text bounded to 2,000 characters. History has an inclusive explicit monitoring-date window <=90 days, limit 1..100 and a validated keyset cursor bound to equipment/date filters; return bounded original/effective before/after, actor/reason/time/revision, never recursively embedded history. These interactive bounds do not impose a retention/export cap.
6. **Storage and compatibility:** add immutable amendment rows; extend the existing immutable event table with reason, proposal link, complete before/after projection and monotonic ordering, retaining uniqueness only for TM-04 creation/deviation events. Each review event stores its complete effective/review projection, so current state reads only the latest relevant event, without replay/fold. Rejection restores the proposal's captured before-state and advances only the revision/event attribution. Keep original `operator_user_id` distinct from `effective_author_user_id` (original operator until an approval changes effective content), plus separate proposal/decision actors and times. Amendment never changes original captured-at, source, note, shift or policy snapshot.
7. **Set-based read projection:** retain the existing slot signature/date/shift/cursor engine. Restrict saved readings to the requested <=90-day window and current authorized equipment/tenant/department before joining events; use a single SQL query and an index on `(reading_id,event_sequence DESC)` to select latest relevant review state. No per-slot PL/pgSQL calls, unbounded full-history fold or recursive JSON aggregation. Single-reading and history RPCs use the same current equipment authorization semantics; history keysets on event sequence with matching index and limit. Preserve TM-04 creation/conflict payload's original `reading`; additive effective/review fields prevent a duplicate response presenting the original as the latest effective content.
8. **Deviation handoff:** approval that makes an initially normal/unable reading abnormal must atomically append a TM-04-compatible `deviation_created` event when none exists, with effective value, breach direction and original captured thresholds/snapshot. Retain exactly one such handoff per canonical reading under its existing uniqueness invariant. A later in-range/unable correction never deletes or closes an existing deviation event; TM-06 owns lifecycle/closure. Approval and its first breach handoff either both persist or both roll back.
