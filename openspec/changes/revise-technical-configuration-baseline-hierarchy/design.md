## Context

`add-technical-configuration-comparison` established an independent technical
configuration dossier, immutable locked baseline versions, supplier options,
criterion-level evidence, manual evaluation, comparison, and Excel workflows. Its
baseline contract intentionally used two levels:

1. editable group;
2. assessable criterion.

The current baseline workbook mirrors the canonical wire contract with visible
machine-oriented columns such as `row_type`, `group_order`, `criterion_order`,
`criterion_code`, and `requirement_text`. It also binds the workbook to one dossier,
baseline version, and revision through hidden metadata.

The discovery examples `basic-config-template.md`,
`basic-technical-config-template.csv`, and
`basic-technical-config-template.xlsx` are examples of document shape, not fixed
business data. Future configurations may contain any number of rows. The stable
document convention is narrower:

- Roman-numbered rows are main sections;
- positive-integer rows are one level of subgroup;
- rows with blank `STT` are detailed criteria.

The discovery XLSX currently contains one off-contract `STT` value,
`TÍNH NĂNG ƯU VIỆT`. It is not a fourth row kind and must produce an actionable
physical-row validation error if that example is uploaded unchanged. Published
templates generated by the application use only the three markers above.

Users need the Roman section and decimal subgroup rows to remain visible for context,
but only detailed criteria receive manual responses, evidence, and assessment.

## Goals / Non-Goals

### Goals

- Represent exactly one subgroup level between a main section and criteria.
- Keep direct criteria under a main section valid.
- Preserve every existing criterion identity and downstream relationship during
  migration.
- Generate and parse a user-facing XLSX with two visible editable columns.
- Support arbitrary row counts and arbitrary counts of sections, subgroups, and
  criteria within explicit safety bounds.
- Keep import preview authoritative and full replacement atomic.
- Show aggregate structural status without double-counting criteria.
- Preserve the current manual criterion evaluation contract.

### Non-Goals

- Arbitrary recursive trees or a `1 -> 1.1 -> 1.1.1` hierarchy.
- Automatic semantic inference from punctuation, capitalization, indentation, cell
  styling, or requirement text.
- Assessment inputs, evidence, notes, or supplier responses on structural rows.
- Weighted scoring or a new ranking algorithm.
- CSV or legacy `.xls` upload.
- Changing supplier-option workbook structure.
- Folding this follow-up into the remaining acceptance tasks of
  `add-technical-configuration-comparison`.

## Decisions

### 1. Use an explicit three-level domain model

The persistent hierarchy is:

1. `baseline group`: main section;
2. `baseline subgroup`: optional structural child of one main section;
3. `baseline criterion`: assessable leaf owned by a main section and optionally one
   subgroup.

An explicit subgroup entity is simpler and safer than a generic recursive tree because
the approved business rule supports only one decimal subgroup level.

Baseline criteria retain their current main-section ownership and add nullable
subgroup ownership. A criterion with no subgroup remains a direct child of the main
section.

A main section may contain both direct criteria and subgroups. Canonical order places
all direct criteria before the first subgroup, followed by complete subgroup blocks.
This keeps the web model and two-column workbook unambiguous: blank `STT` rows before
the first subgroup are direct criteria; after a subgroup marker they belong to that
subgroup until the next subgroup or main section.

The four common Roman-section names are seeded defaults, not immutable identifiers.
“Nearly fixed” describes the recurring procurement-document shape. Draft users may
add, rename, delete, or reorder them, and the system does not silently restore a
deleted suggestion.

Suggested relational shape:

- add an ordered `technical_configuration_baseline_subgroups` table scoped to one
  baseline version and main section;
- add nullable `subgroup_id` to
  `technical_configuration_baseline_criteria`;
- enforce through guarded RPC validation that criterion version, main section, and
  subgroup scope agree;
- keep direct Data API privileges revoked and continue access through guarded RPCs.

Alternatives considered:

- Reusing a criterion as both a heading and an assessable row was rejected because the
  approved behavior has no direct assessment for the heading.
- Flattening every decimal heading into a main section was rejected because it loses
  the stable Roman section context.
- A recursive `parent_criterion_id` tree was rejected because it permits unsupported
  depth and expands migration, UI, and query complexity without a current requirement.

### 2. Derive ordinals from order, not stored user labels

Main-section and subgroup display ordinals are generated from canonical sort order:

- main sections display `I`, `II`, `III`, and so on;
- subgroups display `1`, `2`, `3`, and so on within their main section.

The imported `STT` value identifies row kind only. Its literal number is not a stable
identifier and is not preserved. Reordering in Excel or the web editor produces
normalized ordinals in preview and subsequent downloads.

The parser accepts:

- a valid Roman numeral marker for a main section;
- one positive-integer marker for a subgroup;
- a blank marker for a criterion.

It ignores fully blank rows and trims supported surrounding whitespace. It rejects:

- meaningful content before the first main section;
- a subgroup without a current main section;
- an empty main-section, subgroup, or criterion content cell;
- any nonblank marker that is neither a supported Roman numeral nor a positive
  integer, including discovery-only labels placed in `STT`;
- unsupported deeper numeric notation such as `1.1`;
- unsupported visible columns, sheets, cell value shapes, or workbook versions.

### 3. Structural rows are visible but never directly assessed

Only leaf criteria have:

- supplier response;
- supplementary information;
- citations and evidence;
- technical and evidence axes;
- derived criterion status.

Main sections and subgroups remain visible in the baseline editor, comparison matrix,
evaluation navigator, and result export. They may be collapsed or expanded, but they
do not expose response or assessment controls.

Progress, filtering, ranking inputs, and denominators count each leaf criterion exactly
once. Structural rows never create synthetic criteria or duplicate descendant counts.

Evaluation owns a separate presentation row model. One evaluation-specific canonical
leaf flattener is the only baseline-to-leaf traversal used by evaluation projection,
legacy fallback, navigator rows, progress, and aggregate inputs. Its canonical tuple is:

1. main-section `sort_order`;
2. main-section ID;
3. direct criterion before subgroup criterion;
4. subgroup `sort_order` for subgroup criteria;
5. subgroup ID for subgroup criteria;
6. criterion `sort_order`;
7. criterion ID.

Legacy two-level snapshots are normalized as direct criteria and remain supported.
Navigator heading rows wrap only leaf criteria visible on the current filtered
presentation page. Empty sections and subgroups remain visible in the complete
progress/summary surface, but do not create orphan navigator headings.

The navigator/presentation layer constructs that page-local section/subgroup/criterion
row union exactly once from the canonical leaf page. The navigator pane forwards the
readonly row union and expansion controls; the criterion list renders and filters that
union directly. It does not flatten leaves or rebuild hierarchy independently. This
keeps the active workspace, controlled ancestor expansion, and local collapse on one
presentation contract instead of allowing competing row projections.

Structural rows start expanded. Collapse/expand is local presentation state only:
collapsing hides descendant presentation rows without changing leaf totals, filter
totals, pagination, selected criterion, save/save-next, dirty guards, denominator,
ranking, or score. When filter, page navigation, direct selection, or
`Lưu & tiếp tục` selects a leaf hidden by local collapse state, its section and subgroup
ancestors expand before focus moves to that leaf.

### 4. Aggregate status is transparent and fail-fast

A subgroup aggregates only its direct leaf criteria. A main section aggregates:

- its direct criteria;
- every leaf criterion inside its subgroups.

Aggregate status precedence is:

1. `Chưa có tiêu chí` when the structural row has zero descendant criteria;
2. `Không đạt` when any descendant criterion has derived status `failed`;
3. `Đang đánh giá` when no descendant failed and at least one is `not_evaluated`;
4. `Cần làm rõ` when all descendants are evaluated, none failed, and at least one is
   `unclear` or `insufficient_evidence`;
5. `Không áp dụng` when every non-empty descendant is `not_applicable`;
6. `Đạt` when every applicable descendant is `meets` or `exceeds` and at least one
   applicable descendant exists.

The UI also shows exact descendant counts by existing canonical derived status. An
`exceeds` count is supplementary information and does not replace the aggregate
status with a new structural `Vượt yêu cầu` state.

The aggregate changes immediately after a successful assessment result is adopted
into the authoritative complete cache. Unsaved local assessment drafts do not mutate
the persisted aggregate.

Aggregate status and counts always derive from the complete baseline descendant
universe and the authoritative complete assessment cache. Active filters, transport
pages, comparison pages, navigator collapse state, and unsaved drafts never change the
aggregate input.

Complete-cache adoption distinguishes three states:

- a known-complete cache, including a successfully loaded empty map, receives the saved
  assessment by criterion ID before aggregate refresh;
- a known-empty comparison set created by the current save is seeded with the saved
  assessment;
- an unavailable, loading, or failed cache for an existing comparison set is never
  promoted to authoritative from one saved assessment.

If filtered-navigation refresh fails after persistence succeeds, the UI keeps the
already authoritative aggregate when one exists, exposes an actionable retry state for
the failed filtered read, and never replaces the aggregate with a partial cache.

### 4A. Upgrade the evaluation read contract before hierarchy UI

P5C owns a superseding
`technical_configuration_evaluation_criteria_list(UUID, UUID, TEXT, INTEGER, INTEGER)`
definition. It preserves the existing signature, JSON response shape, accepted
filters, JWT/auth guards, `SECURITY DEFINER` and `search_path`, grants, assessment
persistence, and transport page-size bound of `100`.

The RPC computes `canonical_index` over the complete baseline leaf universe before
applying the status filter. It uses the evaluation canonical tuple defined above,
derives `canonical_page` with the comparison criterion page size `50`, and orders both
the filtered transport page and JSON aggregation by `canonical_index`. Deterministic ID
ties are part of the contract, not an implementation detail.

The read-contract migration is deploy-safe before subgroup data or evaluation UI
activation. The hierarchy UI depends on that migration being present and applied in
the target environment. Creating the local migration does not authorize applying it to
live Supabase; live application requires a separate explicit user approval. Migration
source tests inspect the superseding file directly. Query plans are inspected with
`EXPLAIN` before any index is proposed; P5C does not add speculative indexes.

P5C adds its own hierarchy-order and security phase gates. The stale
`technical-configuration-baseline-hierarchy-apply-migration.test.ts` and
`technical-configuration-baseline-subgroup-mutations-migration.test.ts` assertions
remain owned by Issue #903 and are reported separately rather than changed to satisfy
P5C.

### 5. Introduce a user-facing baseline XLSX contract

The new generated workbook contains:

- visible sheet `Nhập cấu hình`;
- visible sheet `Hướng dẫn & Ví dụ`;
- hidden sheet `_meta`.

`Nhập cấu hình` exposes exactly two visible editable columns:

1. `STT`;
2. `NỘI DUNG YÊU CẦU`.

The sheet uses stable widths, wrapped text, a frozen header, and restrained styles that
distinguish generated section, subgroup, and criterion rows without making style part
of the parsing contract.

Generated workbooks may include hidden identity columns after the two visible columns
to preserve existing main-section IDs, subgroup IDs, criterion IDs, and criterion
codes. The server treats hidden identity as untrusted input and validates ownership
against the selected dossier, version, and revision.

For structural rows, `NỘI DUNG YÊU CẦU` maps to the section or subgroup name. For
criterion rows, it maps to `requirement_text`. The optional criterion `title` is not
an editable XLSX v2 field: a current-data round trip preserves the existing title for
an identity-matched criterion, while a new criterion created from XLSX v2 starts with
`title = NULL`. The web editor remains the authoring surface for criterion titles.

The `_meta` sheet retains versioned ownership metadata:

- template kind and version;
- dossier ID;
- baseline version ID;
- baseline revision;
- generation timestamp.

The instructions sheet is ignored by parsing. The blank template keeps
`Nhập cấu hình` empty and places all examples on `Hướng dẫn & Ví dụ`, preventing
example rows from being imported accidentally.

### 6. Provide two explicit download intents

`Tải cấu hình hiện tại` exports the selected draft's complete hierarchy and hidden
stable identity. It is the default editing round-trip when a draft already contains
data.

`Tải mẫu trống` exports an empty input sheet bound to the selected draft revision. It
is intended for replacing the draft from a newly prepared workbook.

Both actions are draft-only. Locked baselines remain immutable and read-only.

### 7. Keep full replacement atomic and preview destructive effects

Import remains an authoritative full-tree replacement of the selected draft. The
client parses the workbook, but the server independently validates and normalizes the
complete hierarchy before preview or apply.

Preview reports:

- normalized main-section count;
- normalized subgroup count;
- criterion count;
- create, update, move, and delete effects by entity kind;
- provisional criterion codes for new criteria;
- actionable physical-row errors;
- stale dossier, version, or revision conflicts.

Apply:

- revalidates under the existing editable-baseline/revision lock;
- updates compatible stable entities;
- creates new entities;
- moves existing criteria without changing their IDs or codes;
- deletes omitted criteria, subgroups, and main sections in dependency-safe order;
- advances `next_criterion_number` only for new criteria;
- increments baseline revision exactly once;
- rolls back the entire mutation on any failure.

The confirmation command must communicate replacement semantics and deletion counts,
not only the number of uploaded rows.

### 8. Preserve legacy workbook read compatibility

New downloads use the new user-facing workbook version. The parser continues to accept
the existing canonical baseline workbook version during rollout:

- legacy groups map to main sections;
- legacy criteria remain direct children of their main section;
- no subgroup is invented.

The compatibility window may be removed only through a later explicit proposal after
existing generated files are no longer operationally relevant.

### 9. Migrate existing data without changing criterion identity

Migration behavior:

- every existing baseline group remains the same row and becomes a main section;
- every existing criterion keeps its ID, code, group, title, requirement text, order,
  source linkage, citations, option responses, and assessments;
- every existing criterion starts with `subgroup_id = NULL`;
- locked baseline history remains immutable after migration;
- snapshot and copy functions include empty subgroup arrays until subgroups are added
  in a later draft.

Rollback must not discard subgroup relationships after users create them. A deploy
rollback therefore requires forward-only compatibility or an explicit data-preserving
superseding migration, not a destructive column/table drop.

### 10. Keep the parent change independently finishable

This change starts only after its dependency gate confirms the parent change's
mainline contracts and outstanding release work. Its tasks may reference current
implementation files, but each implementation leaf must re-run live schema inspection,
Code Review Graph narrowing, GitNexus impact analysis, and a TDD plan at execution
time.

The parent change's remaining real-world assessment and release checks are not copied
into this task list. This change owns only new hierarchy and workbook behavior plus
the regressions directly caused by it.

### 11. Deliver through small deploy-safe leaf phases

Every implementation leaf maps to one GitHub issue, one branch, and one PR. The
default review budget is roughly 1,500 changed lines per leaf, including focused tests
but excluding unavoidable generated output only when the PR description reports both
the generated and hand-written diff separately.

The line budget is a reviewability target, not a reason to split one atomic database
or contract transition across unsafe deploy states. A larger leaf is acceptable only
when:

- splitting would leave old or new clients unable to use the deployed contract;
- the excess is primarily migration SQL, generated types, or representative fixtures;
- the implementation plan explains why the larger boundary is safer;
- focused review remains possible through file ownership and commit structure.

Deployment order follows expand/migrate/contract principles:

1. add storage without changing existing responses or UI;
2. deploy consumers that tolerate old and new shapes;
3. deploy producers and mutation paths for the new shape;
4. deploy hidden/library-only workbook and aggregate models;
5. wire subgroup-producing authoring/import UI without mounting it on production
   screens;
6. update baseline and comparison readers in separate leaves;
7. deploy the hierarchy-aware evaluation criteria read contract before activating the
   evaluation hierarchy UI;
8. update evaluation/progress and result export in separate leaves;
9. enable server-side subgroup mutations and XLSX v2 apply only after every production
   reader is hierarchy-aware;
10. mount subgroup-producing production controls in a later UI-only leaf;
11. remove compatibility behavior only in a later explicit change.

No leaf may require an unmerged next PR to restore the existing user workflow. New
controls remain absent or disabled until all dependencies needed by that control are
already deployed.

## Risks / Trade-offs

- **Aggregate status may hide mixed outcomes** -> always show exact descendant counts
  and allow expanding the structural row.
- **A full replacement can delete valid work** -> authoritative diff preview, explicit
  delete counts, revision conflict protection, and atomic apply are mandatory.
- **Hidden workbook identity can be edited or lost** -> treat it as untrusted,
  ownership-check every identifier, and fall back to create/delete semantics only when
  preview makes the result explicit.
- **Hierarchy changes touch many read models** -> phase work across schema/RPC,
  workbook, authoring UI, and read-only/evaluation surfaces with contract tests at
  every boundary.
- **Large workbooks can make client preview slow** -> define bounded file/meaningful-row
  limits and paginate or virtualize preview presentation without truncating server
  validation.
- **Two active changes affect one capability** -> enforce the dependency gate and do
  not archive this follow-up before `add-technical-configuration-comparison` becomes
  the canonical capability baseline.
- **A nominal line limit can encourage unsafe splitting** -> treat 1,500 lines as a
  review target while keeping migrations and cross-version contracts atomic.

## Migration Plan

1. Finish and stabilize `add-technical-configuration-comparison`.
2. Add subgroup schema and nullable criterion ownership with existing rows unchanged.
3. Deploy backward-compatible client decoders before RPC responses include subgroups.
4. Deploy hierarchy-aware snapshot/copy/lock/read/write/import RPC contracts in
   dependency order.
5. Release new workbook codec with legacy read compatibility, wire the new download
   and import actions without mounting them on production screens.
6. Wire hierarchy-aware baseline authoring without enabling subgroup creation.
7. Update aggregate models and comparison in separate leaves.
8. Deploy the hierarchy-aware evaluation criteria read contract, then update
   evaluation/progress without changing comparison or result export.
9. Update result export in its own leaf.
10. Run cross-surface regression, then enable server-side subgroup writes.
11. Mount XLSX v2 import/download and subgroup authoring in a UI-only activation leaf.
12. Run representative browser and authorized live-database acceptance.
13. Keep rollback forward-compatible; do not drop populated hierarchy data.
